# api keys consolidation — Plan
**Created**: 2026-08-17 | **Status**: Active

## Summary

The api-key feature is currently split across two surfaces that are not two implementations of one thing — they are one feature with a degraded copy. `web/components/AccountSettingsDialog.tsx:1140-1401` can create with a preset and revoke; it cannot set a ttl, build custom scopes, rotate, or even display what a key is scoped to. `web/app/settings/api-keys/` (page.tsx + CreateKeyDialog.tsx + KeyCard.tsx) can do all of it. Neither has a shared data layer — both are raw `fetch()` against `/api/keys` with no hook in `web/hooks/`.

This plan collapses them into **one organised panel** — an extracted `ApiKeysManager` mounted in the account dialog's `api` section and re-used by a thin `/settings/api-keys` wrapper — and lands four behaviour changes on top: always mint `live` (drop the test option), a `PATCH /api/keys/{keyId}` so scopes are editable, revoke as a soft delete instead of a hard delete of two docs, and a daily expiry-notice email.

Everything here has an in-repo precedent to copy: `PasskeyManager` + `usePasskeys` for the extraction, `api/account/api-keys/route.ts:108` for live-only minting, `webhooks/[webhookId]/route.ts:120-271` for the PATCH shape, `lib/userDeleteCascade.server.ts:161-191` for soft revoke, and `api/cron/health-check/route.ts` for the expiry cron.

## Settled — do not relitigate

1. **Always mint live.** The environment selector is removed from every UI. `environment` is *not* cosmetic — it is the second component of the idempotency cache key (`web/lib/idempotency.ts:10,41,135,261-267`) — so the union `'live' | 'test'` **stays**, no data is migrated, and legacy `owk_test_*` keys keep working forever (auth never reads the field: `apiAuth.server.ts:232-238`).
2. **Server is the enforcement point**, not the UI — SDK and CLI callers get the same guarantee. Incoming `environment` is **tolerated and ignored**, never a 400: `@owlette/cli` v1.0.0-rc.0, `sdks/node/src/resources/keys.ts:46` and `sdks/python/roost/resources/keys.py:77` all still send it.
3. **Rotate keeps inheriting the old key's environment** (`api/keys/[keyId]/rotate/route.ts:128-129`). It is published contract (`openapi.yaml:2509`) and flipping it would re-namespace idempotency mid-flight. Deliberate, documented in the code comment.
4. **The account dialog's `api` section is the primary surface.** `/settings/api-keys` **survives** as a ~30-line wrapper: 9 e2e navigations across 5 spec files, 3 docs references, and `e2e/COVERAGE.md:44` point at the route, and nothing today deep-links a dialog section by URL (`initialSection` is a prop, `AccountSettingsDialog.tsx:79`), so a redirect would require building query-param→section plumbing first.
5. **No client Firestore reads for keys, ever.** `users/{uid}/api_keys` and `api_keys/{keyHash}` are Admin-SDK-only. All reads stay on `GET /api/keys`.
6. **No `firestore.rules` change in any workstream.** Verified per workstream: prefs are allowlisted wholesale (`firestore.rules:653-662`), `users/{uid}/api_keys/{keyId}` is read-own / write-denied and already names `revokedAt` (`:701-708`), `api_keys/{keyHash}` is deny-all (`:712-714`), and `environment` appears only in a descriptive comment (`:703`). Any proposal implying a rules edit is a red flag, not a task.
7. **`revoked` derives as `revokedAt !== null`**, never `<= now` — `apiAuth.server.ts:199` is a plain truthiness check, so a future-dated stamp already 401s.
8. **All copy lowercase**, `lucide-react` only, theme tokens only.

## Approach

### A. Consolidate the UI (Wave 2)

- New `web/hooks/useApiKeys.ts` exposing `{ keys, loading, refresh, createKey, rotateKey, revokeKey }` — modelled on `web/hooks/usePasskeys.ts:9` (fetch-based, not Firestore). It replaces six inline fetch sites: `settings/api-keys/page.tsx:29-48`, `AccountSettingsDialog.tsx:203-214/:1225-1248/:1334-1352`, `CreateKeyDialog.tsx:103-129`, `KeyCard.tsx:85-104/:106-124`.
- New `web/components/ApiKeysManager.tsx` with a `compact` prop — the exact `PasskeyManager.tsx:26` shape, mounted `compact` in the dialog (`AccountSettingsDialog.tsx:1133-1135` is the precedent one section above) and full-size on the page.
- Create moves in as **inline disclosure, not a nested modal**. Width is not a constraint: the dialog gives the scope builder ~656px (`sm:max-w-4xl` 896 − 192 sidebar − 48 padding) vs CreateKeyDialog's ~528px today.
- Panel order: header → reveal banner (fed by **both** create and rotate) → your keys → create key → usage snippet.
- Four hook-level divergences settled: revoke **refetches** (not local filter); the dialog's expired/retired-last **sort wins**; `CreateKeyDialog`'s client-side **name validation wins**; `now` comes from the existing `web/hooks/useMinuteTick.ts` singleton so "expiring soon" and "rotated (grace)" go live.

### B. Remove the test environment (Wave 1)

One exported constant `MINTED_API_KEY_ENVIRONMENT = 'live'` in `web/lib/apiKeyTypes.ts`, imported by the two mint routes that still branch (`api/keys/route.ts:189`, `api/cli/device-code/authorize/route.ts:246`). `api/account/api-keys/route.ts:108` already hardcodes live — it is the precedent. Three UI surfaces, not two: `CreateKeyDialog.tsx:192-208`, `app/cli/authorize/page.tsx:141-157`, and the account dialog (which never had a selector). OpenAPI request enums are marked `deprecated: true` but **keep `[live, test]`**; response enums keep both values permanently.

### C. Editable scopes — `PATCH /api/keys/{keyId}` (Wave 3)

Extract `validateScopes` + the grantability gates out of `api/keys/route.ts` into `web/app/api/keys/_shared.ts` so POST and PATCH cannot drift, then add PATCH beside DELETE in `api/keys/[keyId]/route.ts`. The write is a `db.batch()` touching **both** docs — the same shape as `rotate/route.ts:142-184`. Full-array replacement semantics, no merge, `[]` rejected.

### D. Soft-delete revoke (Wave 4)

Stamp `revokedAt` instead of deleting, on **both** revoke routes. The auth path already handles it (`apiAuth.server.ts:199-201` checks `revokedAt` *before* `retiresAt` and `expiresAt`, and the lookup is read live with no cache), so this needs **zero auth-path changes**, fails closed just as immediately as a delete, keeps the keyHash→userId mapping attributable for post-revocation replay, and preserves the documented rollback at `docs/runbooks/upgrade-2.12.0.md:556`.

### E. Expiry alerts (Wave 5)

A daily `GET /api/cron/api-key-expiry` on the `health-check` scan-decide-stamp shape (not the digest queue-drain shape — there is no queue here). T-14 / T-3 / T-0 ladder, one email per owner listing all their expiring keys, notice state stamped **before** send on the user-subcollection doc only.

## Risks

- **Silent e2e breakage from restyling during the Wave 2 move.** The settings specs bind to structural selectors, not testids; the route surviving does not protect them. Move markup verbatim, defer visual redesign.
- **Stale lookup doc (Wave 3).** A PATCH writing only the user doc produces a UI claiming reduced scopes while the credential retains full access forever. One batch, both docs, with the unit assertion on `api_keys/<hash>.scopes`.
- **Rotation grace defeats a scope reduction (Wave 3).** The predecessor's lookup stays live with original scopes until `retiresAt` (`rotate/route.ts:176-182`, honoured at `apiAuth.server.ts:203-207`). 409 any PATCH on a key with `rotatedAt`; for a successor with `rotatedFromKeyId`, either apply the new scopes to the predecessor's lookup in the same batch or warn naming its `retiresAt`. Never silently ignore.
- **Privilege escalation (Wave 3).** `validateScopes` checks shape only; the superadmin and site-access gates are separate inline code. A PATCH wired to validation alone lets any member escalate a live key to `user:*:admin`. Shared helper + duplicated `it.each` rejection test.
- **Empty `scopes: []` (Wave 3)** puts a live key on the legacy-bypass branch (`apiAuth.server.ts:221-228`). Keep the non-empty guard as the only path to the field.
- **NOT_FOUND on the lookup (Wave 4)** would leave a key neither revoked nor deleted — still fully authenticating — while the UI toasts "key revoked". Merge-set, one atomic commit, pinned by a lookup-absent unit test. Do **not** split it into a fire-and-forget `.catch()`.
- **Cross-user leakage (Wave 5).** `collectionGroup` under the Admin SDK returns every user's keys flat; a grouping bug puts one customer's key names in another's inbox. Derive the owner from `doc.ref.parent.parent.id` and assert it matches the uid the recipient email was read from before rendering.
- **Duplicate emails (Wave 5)** from double registration or scheduler retry. Stamp before send and accept health-check's stated trade: a lost email beats an alert loop.
- **Unregistered cron fails silently** (`web-deployment.mdx:169-175`) — the feature simply never fires, with no error anywhere.
- **`sweepExpiredApiKeysDaily` is inert** (`apiKeyExpire.ts:50`). Pre-existing defect, surfaced by two workstreams. File it; do not build on it without fixing it first.
- **Someone "improves" the panel into a client `onSnapshot`** — that would require loosening `firestore.rules` and would expose key metadata to the client SDK. Reject on sight.
